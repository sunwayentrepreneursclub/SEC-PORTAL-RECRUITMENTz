Where the Gemini key lives

The Generate draft questions button calls a server-side function, not Gemini directly. The API key sits in that function's environment variables and is never sent to the browser. A key placed in this page's JavaScript would be readable by every visitor.

portal (browser)
   POST /api/generate-questions   { positionId, title, duties }
      ↓
server function  ← GEMINI_API_KEY (env var, club-owned account)
      ↓
returns 5 draft questions → saved as DRAFT, not published

Access control — not what this prototype does

This prototype unlocks on a single password held in the page's JavaScript. Anyone can read it in view-source, so it demonstrates that a gate exists rather than being one. The built version needs two changes:

1. The check runs on the server. A client-side password protects nothing.
2. Each reviewer has their own login. Decisions and reviewer notes are recorded against a person's name — a password shared by four people makes that attribution meaningless, and you can't revoke one person's access when they leave the committee without locking everyone out.
